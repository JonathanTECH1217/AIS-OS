# Airtable: the Monarc CRM base

Written 2026-09-15 when the CRM was built. Base "Monarc CRM", id `appgv3njf5Fk99QXo`, workspace "My First Workspace" (`wspjyXGp11qGY6DF1`), Jonathan's account. Two ways in:

| Who | Mechanism | Used for |
|---|---|---|
| The AIOS in a Claude Code session | Airtable MCP server (`.mcp.json`, `https://mcp.airtable.com/mcp`, OAuth) | Schema changes, seeding, and the writes that make the activity log fill itself (`/inbox` emails, calendar meetings) |
| The dashboard, `python scripts/crm_server.py` | REST API with a personal access token, `AIRTABLE_PAT` in `%USERPROFILE%\.monarc\secrets.env` | Everything Jonathan does on screen |
| The booking backend, `scripts/avmarketing-booking.gs` (added 2026-09-23) | REST API from Google Apps Script with its own token, `AIRTABLE_TOKEN` in the script's properties | One Leads row per booking from monarcbuild.com, Status Booked, UTM string and links by name (`references/apps-script-booking.md`) |

The dashboard runs locally on purpose: a claude.ai artifact cannot reach Airtable (its sandbox blocks fetch, and its connector bridge only reaches claude.ai connectors, not `.mcp.json` servers). The token stays in the Python process and never reaches the browser.

## The token

Create at https://airtable.com/create/tokens. Scopes: `data.records:read`, `data.records:write`, `schema.bases:read`. Access: only the Monarc CRM base. Put `AIRTABLE_PAT=pat...` on its own line in `secrets.env` (rules in `references/credentials.md`). Check without printing it: `python scripts/crm_server.py --check`.

## Plan limits that shape the design

- Free: 1,000 records per base, about 1,000 API calls per workspace per month, 5 requests per second. Team ($20 per seat per month): 50,000 records, 100,000 calls.
- The server is local-first so Free holds: the 887-row dial queue is the CSV on disk; a Company record exists only once touched; no-contact dials bump two fields instead of creating an Activity; the whole base is cached for 120 s and every write is applied to the cache; failed or offline writes queue in `projects/crm/outbox.jsonl` and replay in order on the next request, mapping local ids to real ones.
- Settings in the dashboard shows records against the cap and API calls per session. Past `record_warn` (850) set Config `create_company_on` to `connect`, or move to Team.

## Write rules (every writer, MCP or REST)

1. **One company per Key.** `Key` = website domain with `www.` stripped (`outreach_common.norm_domain`), else `tel:` plus the last 10 digits. Look the Key up before creating. A regenerated CSV with the same domain merges by Key.
2. **One person per Person key.** Lowercased email, else `tel:` plus 10 digits, else `name|companykey`. Look it up before creating.
3. **One open deal per company.** Find the deal with Closed unchecked before creating another. A dial never moves a deal backwards.
4. **An open deal carries a next action, its date, and an owner. A closed deal carries a Close reason.** The server returns 422 without them; MCP writers follow the same rule by hand.
5. **Activities from outside the dashboard carry an External id** (email Message-ID, Calendar event id) and are looked up by it before creating. `Logged by` names the writer: `AIOS inbox` or `AIOS calendar`.
6. **Dates:** Last dial, Close date, Next action date are `YYYY-MM-DD` in Eastern. When is ISO 8601 with an offset (`2026-09-15T16:25:31-04:00`); Airtable returns it as UTC (`...Z`).
7. **Links** are arrays of record ids. The REST layer sends `typecast: true`, so a Source may also be given by name (`["cold"]`), which is how offline writes replay.
8. Never store a password, a token, or a price that is not on `context/offer.md`.
9. **Phase is computed, never typed.** The server recomputes it after every dial, activity, and deal write (`sync_phase`) and `POST /api/rephase` backfills every company. Called = any dial. A channel counts on a connected call (contact-class outcome), an Email, a Text, or a DM activity. Meeting booked = a deal at Booked or later, a Booked outcome, or a Meeting activity. Signed = a Won deal. It never moves down. An MCP writer that adds an Email, Text, or DM activity should follow with `POST /api/rephase` on the running server, or leave it: the next dashboard write on that company catches up.
10. **A campaign push counts every dial (2026-09-25).** While Config `active_campaign` names a Campaigns row, every dial gets an Activities row with `Campaign` linked, no-answer included (the no-contact shortcut under Plan limits is off for the push). The dashboard does this on its own. A row typed straight into Airtable counts once Campaign and Outcome are picked; Type may be left blank and still counts as a dial (formulas and the server changed 2026-09-26, `_is_dial`), and Company should be picked so the company's Phase moves. Connect rate and booking rate then read off the campaign row, Today's campaign card, and Channels, Cold call. The dashboard caches the base for 120 s; Refresh on the Today campaign card pulls hand-typed rows in at once. Blank the Config value when the push ends so no-contact dials go back to bumping the company only.

## REST shapes the server relies on

Endpoint `https://api.airtable.com/v0/appgv3njf5Fk99QXo/<TableName>`. List: `pageSize=100`, follow `offset` until absent. Create and update: at most 10 records per request, body `{"records": [{"fields": {...}}], "typecast": true}` (update adds `"id"` per record, method PATCH). Errors: `{"error": {"type": "INVALID_MULTIPLE_CHOICE_OPTIONS" | "UNKNOWN_FIELD_NAME" | ...}}`, 429 on rate limit (sleep 30 s).

Record shape: `{"id": "rec...", "createdTime": "...Z", "fields": {...}}`. Unchecked checkboxes and empty fields are absent, single selects are bare strings, links are `["rec..."]`, rollups and formulas are numbers or dates, dateTime is UTC ISO.
